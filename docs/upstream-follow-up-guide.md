# Spec Kit 官方版本全面跟进指南

本文档用于指导 AI 比较本地 Spec Kit 与官方最新稳定版本，并形成选择性的升级方案。
它定义调查边界、判断原则和最低输出要求，但不规定固定命令、评分公式、文件清单或执行
顺序。AI 应根据调用时的官方仓库、本地实现、工具条件和模型能力自主选择合适的调查方法。

本文档既可用于只读分析，也可在用户明确要求完成 follow-up 时指导后续实施。只读分析不
代表授权实施升级、删除本地能力或修改版本基线；实施范围与权限应由具体任务确认。只有
选定的升级与瘦身内容已经落地并通过验证，才算完成一次 follow-up，届时必须更新 README
中的官方对齐基线。

## 调用方式

调用时直接要求 AI 阅读本文档即可。AI 必须主动访问官方仓库
<https://github.com/github/spec-kit>，从官方 Releases、Tags 和仓库状态确认调用时的最新
稳定版本，并将其作为默认目标版本，不要求用户事先提供。不得依赖模型记忆、旧对话或本地
缓存声称“最新”。如果 Release 与 Tag 指向不一致、最新条目是 prerelease/draft、官方版本
不可访问，或“最新稳定版”存在歧义，应陈述证据与限制；默认不把 prerelease、draft 或仅有
未发布提交的主分支当作稳定目标，除非用户明确指定。

本地起始基线必须从本仓库 `README.md` 中的 `upstream_baseline` 标记读取。不得要求用户
重复提供 README 已记录的信息，也不得仅凭本地包版本、Git Tag 或 AI 记忆推断官方基线。
如果 README 缺少标记、格式不明确，或与其他基线元数据冲突，应把它列为阻塞项或待确认
事实，不能擅自选择一个基线继续形成确定结论。

示例：

> 阅读 `docs/upstream-follow-up-guide.md`，自动获取官方 Spec Kit 最新稳定版本，以
> `README.md` 记录的官方对齐基线为起点，给出并完成选择性升级与瘦身方案。

用户仍可显式指定其他官方目标版本；否则始终采用调用时查得的最新稳定版本。版本范围只是
调查入口。AI 不得预设目标版本中的所有变化都有本地价值，也不得把官方版本号直接当成
本地版本号或升级完成的证明。

## 跟进目标

“跟进官方”是对官方演进和本地存量的一次双向审视，不是功能增量搬运。AI 必须同时
调查官方的新增、修改、删除、替换、弃用、合并、降级和简化，并判断这些变化对本地的
实际意义。

调查应覆盖 Spec Kit 的完整产品与工程形态，包括但不限于：

- 产品能力、CLI、命令、参数、公共接口和用户可见行为。
- Spec 驱动工作流、阶段划分、节点职责、流转条件、人工与 AI 的分工，以及过程产物。
- Prompt、模板、Agent 或模型使用方式、上下文组织和指令加载策略。
- 安装、初始化、升级、分发、集成方式，以及操作系统、终端和平台兼容性。
- 配置、目录结构、状态管理、扩展机制、依赖和兼容策略。
- 验证、测试、安全、权限、错误处理、可观测性、维护方式和用户文档。

上述维度不要求都产生升级建议，但报告必须能说明它们已经被合理检查。AI 还应主动识别
未列出的重要变化面，不能因本指南的列举而缩小探索范围，也不能只分析 Release 中最显眼
的新功能。

## 事实与证据

优先使用官方 Release、Tag、提交历史、实际代码、测试和文档等一手资料。Release 摘要
可用于发现线索，但不能代替对版本范围内实际变化的核查。必要时应追踪变化产生的背景、
被解决的问题、后续修正以及官方提供的替代路径。

同时以本地源码、测试、配置和文档确认本地现状，避免仅根据名称推断能力是否相同。比较
时应区分：

- **事实**：能够由官方或本地证据直接支持的内容。
- **推断**：根据证据形成、但仍存在不确定性的解释。
- **建议**：结合本地目标、成本和风险给出的取舍。
- **未知**：现有证据不足、需要进一步验证或由人决定的事项。

报告中的重要结论应可追溯到证据。资料不可得或证据互相冲突时，应明确说明限制，不得把
猜测包装成官方事实或确定结论。

## 本地价值判断

每项重要变化都应放回本地上下文评估，而不是因为“官方新增”就默认引入，或因为“本地
已有”就默认保留。判断至少考虑：

- 本地是否已有等价、部分重叠或更适合当前用户的实现。
- 官方变化所解决的问题是否真实存在于本地，严重程度和发生频率如何。
- 引入后是否改善实际效果、可靠性、易用性、兼容性、维护效率或长期演进能力。
- 官方设计是否与本地自研工作流、Codex 定位、使用环境和用户习惯兼容。
- 收益是否值得迁移成本、认知负担、复杂度、回归风险和持续维护成本。
- 应原样采用、吸收设计思想后本地适配，还是以现有实现解决同一问题。

对重要变化给出清晰处置意见，可使用以下语义，也可采用同等清晰的表达：

- **建议引入**：本地存在明确价值，适合纳入升级方案。
- **适配引入**：认可目标或设计思想，但应结合本地架构重新实现。
- **暂缓观察**：当前证据、成熟度或收益不足，保留后续复查条件。
- **不引入**：无本地价值、已被更合适的能力覆盖，或成本与风险明显高于收益。
- **删除或瘦身**：官方变化暴露了本地存量的冗余，或独立评估表明本地应进一步简化。

“不引入”和“删除或瘦身”都是正式分析结果，必须像建议引入项一样给出客观理由，而不是
作为遗漏项处理。

## 删除、替换与瘦身

AI 必须专门调查官方删除、合并、弃用、降级或不再强调的能力，理解其历史用途、删除原因、
替代路径和兼容影响。官方没有在 Release 中突出说明的删除也不能默认忽略。

在此基础上反向审视本地存量，尤其关注：

- 为较弱模型能力设计、如今可能已无必要的繁琐提示、机械步骤和过度约束。
- 职责重叠的工作流节点、重复文档、重复验证和低价值中间产物。
- 为旧安装方式、旧平台限制或已消失兼容问题保留的机制。
- 官方已简化、替换或取消，而本地仍持续承担维护成本的历史设计。
- 本地自研过程中形成、即使官方仍保留也已不再产生足够价值的复杂度。

模型能力变强只是一条调查线索，不是删除依据。瘦身建议必须验证相关机制当前保护的真实
风险、治理价值和环境差异；也不能因为官方删除某项能力就机械跟删。对建议删除、合并或
降级的本地能力，至少说明：

- 它目前承担的作用和使用者。
- 建议瘦身的证据与理由。
- 删除后的替代路径或为何不再需要替代。
- 兼容性、迁移和回归风险。
- 如何验证瘦身没有损害必要能力。

## 最低输出要求

具体报告结构、比较工具、调查顺序和分类粒度由执行时的 AI 决定，但最终结果至少应包含：

1. 本地基线、官方目标版本、证据来源、调查范围和已知限制。
2. 官方主要变化全景，清楚覆盖新增、修改、删除、替换、弃用和简化。
3. 官方变化与本地实现的关系，标明已覆盖、部分覆盖、缺失、冲突或不适用。
4. 建议引入项的实际价值、适配方式、依赖、成本和主要风险。
5. 明确不引入项及其客观理由。
6. 本地删除或瘦身候选，包括官方删除带来的启示和基于当前模型能力的独立判断。
7. 分阶段升级建议，区分必要升级、可选优化、观察项和删除项，并说明合理的先后关系。
8. 仍需验证的未知信息、需要人作出的关键取舍，以及这些事项对方案的影响。

报告应优先呈现影响大、证据充分的变化，不以提交数、文件数或功能数量冒充分析质量。
若某个检查维度没有值得采取的变化，应明确给出“已检查、暂无建议”及必要说明。

## 基线更新与 follow-up 闭环

应严格区分“完成分析”和“完成 follow-up”：

- 只完成版本调查、价值评估或升级方案时，不得修改 `README.md` 的
  `upstream_baseline`，因为它表示已经完成的本地对齐状态，而不是分析目标。
- 用户授权实施后，应落实最终选定的引入、适配和瘦身项，并完成与变更风险相称的验证。
- 即使部分官方变化被客观判定为不引入，只要版本范围已被完整评估、选定事项已实施并验证，
  本地也可以声明已跟进到该官方目标版本；“对齐”表示已审查并作出有证据的取舍，不表示
  文件或功能与官方完全相同。
- follow-up 完成后，必须把 `README.md` 中的 `upstream_baseline` 更新为实际完成跟进的
  官方目标 Tag，并保持原有“本地版本独立演进”的语义。若仓库中存在同义的机器可读基线
  元数据，也应检查并按其真实语义同步，避免基线互相矛盾。
- 若实施或必要验证尚未完成、仍有阻塞项，或者只审查了目标版本范围的一部分，则不得提前
  更新基线。报告应保留原基线，并明确距离闭环还缺什么。

基线更新本身也应纳入最终差异检查和验证证据。最终报告须明确记录旧基线、新基线、目标
版本的官方来源、未引入项的处置理由，以及验证结果。

## 完成标准

一次跟进分析只有在满足以下条件时才算分析完成：

- 没有把跟进退化成新增功能列表，也没有默认追随官方全部变化。
- 已检查官方删除、替换和简化，并据此审视本地是否需要瘦身。
- 已覆盖工作流、节点职责、安装升级、模型与上下文、工程质量等不同变化面。
- 对本地已有能力进行了事实核对，而不是仅按文件名或术语匹配。
- 建议引入、不引入、适配、观察和瘦身项都有可解释的判断依据。
- 模型能力演进被纳入考虑，但没有成为未经验证的删除理由。
- 事实、推断、建议和未知保持可辨识，重要结论可追溯。
- 方案保留未来实现选择，不在缺少授权时直接修改基线或执行升级。

一次完整 follow-up 还必须满足：选定变更已经实施、必要验证通过、未引入项已有明确结论，
并且 `README.md` 的 `upstream_baseline` 已更新到实际完成跟进的官方目标版本。任何一项未
满足，都只能报告为分析完成、部分完成或受阻，不能宣称 follow-up 已闭环。

本指南不预设任何特定版本的差异或最终取舍。每次跟进都应以当时可获得的官方事实、本地
需求和运行环境重新判断。
